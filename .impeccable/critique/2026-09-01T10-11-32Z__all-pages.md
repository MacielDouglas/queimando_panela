## Anti-Patterns Verdict

**Parece AI-generated?** Não de forma flagrante. A voz editorial Epirus (papel, tinta, barro) é genuinamente distinta e foge do template cream/beige genérico. A home tem personalidade. Porém, **duas superfícies quebram a ilusão completamente**:

### LLM Assessment

**O que funciona**: A home é editorial com personalidade. Fraunces com tracking agressivo dá voz. O 404 é memorável. O recipe detail com polaroid CTA é criativo. A paleta Epirus é coesa nas páginas principais.

**O que quebra**: As auth pages (login/criar-conta) usam `stone-400`, `stone-300`, `stone-100`, `bg-taupe-900` — classes que não existem no globals.css e não fazem parte do design system. Parecem de outro site. A minha-conta usa `border-2 border-[#1b2920]` hardcoded, inconsistente com as bordas finas `var(--line)` do resto. O error.tsx e unauthorized.tsx também usam `border-2` pesado. Essa fragmentação visual é o maior tell de "different AI sessions stitched together".

## Overall Impression

**O maior problema é a dualidade visual.** A home e as páginas de receitas falam Epirus com fluência. As auth pages e minha-conta falam outro idioma — literalmente usam classes de cor que não existem no CSS. Um usuário que navega de `/receitas` para `/login` sente que trocou de site. O potencial é alto: quando o design system é respeitado, o resultado é editorial, quente e memorável. Quando não é, parece prototype genérico.

## What's Working

1. **A paleta Epirus é genuinamente distinta** — papel #f6f0e4 + tinta #1b2920 + barro #a85131 cria uma assinatura visual que foge do cream/beige AI default. Nosso "paper" é editorial, não "sand".

2. **O 404 é excelente** — piadas rotativas, confetti, QPMark, e a piada final "peça pizza" mostra personalidade sem ser forçado. É o tipo de 404 que as pessoascreenshotam.

3. **O CTA "Sua vez" no recipe detail** — o efeito polaroid com hover rotate, a frase "Panela > perfeição", e o badge "olhômetro aprovado" combinam delight com propósito. Não é decorativo; comunica a essência do produto.

## Priority Issues

### [P1] Auth pages usam paleta fora do design system
- **O que**: login/criar-conta usam `stone-400`, `stone-300`, `bg-taupe-900` — classes não documentadas no globals.css. Resultado: textos com contraste potencialmente inadequado e visual completamente desconectado do resto.
- **Por que importa**: Um usuário que vem da home sente que trocou de produto. A confiança construída pelo design editorial se quebra no momento do login — exatamente quando o usuário precisa confiar o suficiente para criar conta.
- **Fix**: Migrar login/criar-conta para usar as variáveis Epirus: `var(--cocoa)`, `var(--food-accent)`, `var(--cream)`, `var(--line)`. Usar o AuthShell existente (que já é Epirus) como base, ou alinhar a paleta.
- **Comando sugerido**: `$impeccable colorize` — aplicar paleta Epirus nas auth pages

### [P1] Minha-conta usa border-2 hardcoded e cores inline
- **O que**: `border-2 border-[#1b2920]` em header, cards e dados. Cores `#a85131`, `#1b2920`, `#3e4d42`, `#e8ddca` hardcoded em vez de variáveis CSS. A seção "Verificada" usa `bg-[#a85131]` com `text-[#1b2920]` (barro sobre tinta = contraste ruim).
- **Por que importa**: Inconsistência visual e problema real de acessibilidade. Barro sobre tinta não atinge 4.5:1.
- **Fix**: Substituir hardcoded por variáveis. Trocar `border-2` por `border` (1px) com `var(--line)`. Corrigir contraste da tag "Verificada".
- **Comando sugerido**: `$impeccable polish` — alinhar minha-conta ao design system

### [P2] Error e Unauthorized usam border-2 pesado
- **O que**: error.tsx e unauthorized.tsx usam `border-2 border-[#1b2920]` + `box-shadow: 8px 8px 0` (not-found). Estilo "quadrado e amarelo" que é anti-reference do PRODUCT.md.
- **Por que importa**: Quebra a consistência com o design editorial suave. O not-found está no caminho certo (usa variáveis), mas error e unauthorized são duros demais.
- **Fix**: Substituir `border-2` por `border` + `var(--line)`. Usar sombras Epirus (`var(--shadow-sm)`) em vez de `box-shadow` manual.
- **Comando sugerido**: `$impeccable polish`

### [P2] LogoutButton usa componente genérico com stone-300
- **O que**: `rounded-none border-stone-300` — shadcn Button padrão sem personalidade Epirus.stone-300 não existe no design system.
- **Por que importa**: Botão de logout é interação de alto risco (deslogar). Deveria usar a vocabulário visual do resto do produto.
- **Fix**: Usar `button-outline-queimando-panela` ou alinhar com o estilo Epirus.
- **Comando sugerido**: `$impeccable polish`

### [P3] Login/criar-conta duplicam AuthShell com visual diferente
- **O que**: Existem 2 pares de auth: `/sign-in` + `/sign-up` (usam AuthShell Epirus) e `/login` + `/criar-conta` (usam layout split com stone/taupe). Dois sistemas de auth visual para o mesmo fluxo.
- **Por que importa**: Confunde usuários. Qual é a rota correta? Qual visual é "oficial"?
- **Fix**: Consolidar em um único design. Manter AuthShell como padrão e redirecionar rotas antigas, ou unificar visualmente.
- **Comando sugerido**: `$impeccable distill`

## Minor Observations

1. **Recipes page repete eyebrow** "Receitas com história" —一个 eyebrow por seção é vozes; repetir é scaffolding de AI.
2. **CtaSection usa `rgba(31, 41, 51, 0.82)`** — cor não documentada. Usar `var(--ink-muted)` ou `rgba(27, 41, 32, 0.82)`.
3. **Loading skeleton usa `rounded-[var(--radius-md)]`** — resolve para 0px, ou seja, todos os placeholders são quadrados. Deveria refletir o radius real dos cards (18px).
4. **Recipe detail polaroid usa `borderRadius: 10px`** — fora da escala. Usar 14px (radius-sm).
5. **NotFound usa cores hardcoded** `#1b2920`, `#a85131` em vez de variáveis. Funciona, mas quebra o padrão.
6. **LatestRecipesSection é client component** com useState — necessário para o carousel, mas poderia ser server component com searchParams para URL-based navigation (melhor para SEO e sharing).

## Questions to Consider

1. **Por que existem 2 pares de auth (sign-in/sign-up E login/criar-conta)?** É intencional ou debt técnico? Consolidar eliminaria confusão visual e de rotas.

2. **A minha-conta deveria ter o mesmo visual editorial das outras páginas?** Hoje ela parece um admin panel genérico. Se "receita tem dono", o perfil do autor deveria sentir-se como extensão da experiência editorial.

3. **O editor de receitas precisa de autosave?** Para um público 30-55 que pode não ser技术_savvy, perder uma receita escrita é frustrante o suficiente para não voltar. Autosave com draft recovery é low-hanging fruit para retenção.

4. **A inconsistency entre `rounded-none` (reset-password fallback) e `radius-md` (cards) é intencional?** O fallback tem `rounded-none` que contradiz o design system.
